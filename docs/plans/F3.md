# F3 — Locked by the monitor

Created: 2026-10-27 08:55 -05:00 · Edited: 2026-10-27 08:55 -05:00

**Status:** gate crossed 2026-10-27 ("d14 is ratified"); building · **Milestone:** v1.0 · **Owner:** agent · **Delivers:** D14 (FR3 behaviour when the monitor refuses)

Learning level 5%, locked (`O2`); every task is `owner: agent`.

## What the user gets

When the Dell's Smart HDR is on, the monitor greys out Brightness and Contrast in its own menu and ignores every DDC write to them (`C3`). Today the app shows live sliders that do nothing. After F3 the two sliders are disabled, a greyed line under them says "Locked by the monitor's Smart HDR — turn it off in the monitor's menu", and `monitorctl set brightness` prints the same instead of writing silently. Shortcuts and URL actions get the same refusal as a dialog or log line.

## Decision

`D14`, ratified by the owner 2026-10-27: show a monitor-side lock instead of dead sliders. Vendor-keyed like PiP (NFR8): Dell only, preset code `0xF0` value `0x34`, until another monitor shows the behaviour.

## Tasks

### F3-T1 — Lock detection in MonitorCore

Owner: agent · Delivers nothing user-visible (foundational) · `VCP.lockingPresets`: per-vendor table `{ code, values, label }`, Dell `0x10AC → (0xF0, [0x34], "Smart HDR")`. `Monitor.pictureLock() throws -> String?` reads the code only when the vendor is in the table **and** the monitor advertises the code; returns the label when the value is in the set. `Monitor.set` refuses brightness and contrast with `DDCError.locked(code, label)` while the last lock read said locked, so every write path (menu, CLI, URL, intents) is covered by the one funnel. Checkpoint: `swift test --filter LockTests` green; `M10` (ignore the vendor key) and `M11` (write despite the lock) seen red.

### F3-T2 — Menu and CLI

Owner: agent · Delivers D14 · `MonitorState.lockedBy` read in `readValues`; the two sliders disabled with "locked" in the value column and one greyed line under them; `monitorctl list` prints `locked by Smart HDR` beside brightness; `monitorctl set brightness|contrast` reads the lock first and fails with the message. `Actions` reports `DDCError.locked` as the same sentence. Checkpoint: with Smart HDR on, the menu shows the line and `monitorctl set brightness 50` exits 1 with the message; with Smart HDR off, both work as before.

## Design notes

- One extra DDC read (`0xF0`) per refresh, only on a monitor whose vendor is in the table. Writes do not re-read; they trust the last refresh, which is also what the sliders show.
- Only value `0x34` is known. Smart HDR has four modes (Desktop, Movie HDR, Game HDR, DisplayHDR 400); the owner saw `0x34` with Desktop. Other values are an owner item (`O15`): with each mode on, `monitorctl get 0xF0`.
- Not a write path change for any other code: the whitelist (`D3`) is untouched.
