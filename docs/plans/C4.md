Learning level 5%, locked (`O2`); every task is `owner: agent`.

## Baseline (measured 2026-10-27, before any change)

| What | Number | Command |
|---|---|---|
| App footprint after 3 d 22 h running | 26 MB, peak 27 MB (NFR2: under 30 MB) | `footprint -p $(pgrep -x MonitorMenu)` |
| Of which the app's own heap | about 7 MB; the rest is AppKit, AppIntents and the dyld shared cache | `heap --sortBySize <pid>` |
| `monitorctl get brightness` | 2.8 s wall | `/usr/bin/time -p monitorctl get brightness` |
| Discovery alone (registry scan plus probe) | 0.06 s | `/usr/bin/time -p monitorctl bogus` |
| Capabilities string | 493 bytes, read in 38-byte fragments, about 2.3 s | `monitorctl capabilities \| wc -c` |
| Suite | 29 tests, 0 failures; floor 29 | `swift test` |
| Build warnings | 0 | `swift build` |

The 2.8 s is the capabilities read. The app pays it once per launch per monitor (and keeps the result in memory until it quits); `monitorctl` pays it on **every** invocation because a process cannot remember. That is the one large speed defect.

## Tasks

### C4-T1 — Capabilities cache shared by the app and the CLI (speed)

Owner: agent · `CapabilitiesCache` in MonitorCore: the raw string per monitor key (`MonitorIdentity.key`, the serial) in the shared defaults suite `dev.marty.MonitorMenu`. The app's `discoverSync` and the CLI's `load` use memory, then the cache, then the monitor. **Rescan Displays** in the menu and `monitorctl capabilities` (the diagnostic verb) always read the monitor and overwrite the cache; `monitorctl --fresh` does the same for any verb. The whitelist is still the monitor's own string (NFR5); it was read from the same monitor, by serial. Checkpoint: `monitorctl get brightness` under 0.5 s; second app launch reads no capabilities; `M12` (serve a cached string to a different monitor) seen red.

### C4-T2 — Memory (measure, then trim what is the app's)

Owner: agent · Measure a fresh launch, after ten menu opens, and after an hour, against the 26 MB baseline. Trim what belongs to the app: create the switcher panel on first use, reuse the two status-bar images, pass the name resolver into the switcher instead of creating one per show. Checkpoint: numbers in the evidence table; footprint not above baseline; no growth across ten menu opens.

### C4-T3 — Startup and menu-open timing

Owner: agent · Log the time from launch to the first discovery result and from menu open to the refreshed values, before and after T1. Checkpoint: numbers in the evidence table; startup to a usable menu under 1 s with a cached capabilities string.
