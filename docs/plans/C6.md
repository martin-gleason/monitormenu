# C6 — Homebrew distribution: notarized DMG, cask, release procedure

Created: 2026-10-30 09:50 -05:00 · Edited: 2026-10-30 09:53 -05:00

**Status:** gate crossed 2026-10-30 ("let's build this for homebrew. and update the github page to reflect you can get it with homebrew", which also ratifies `D23`); built 2026-10-30; the first published release waits on `O16`.

Learning level 5%, locked (`O2`); every task is `owner: agent` except the one keychain step only the owner can perform.

## Why

The Mac App Store cannot take the app (`docs/learnings/2026-10-30-app-store-feasibility.md`, `D23`). Every DDC app on the Mac ships the same other way: a Developer ID signed, notarized, stapled bundle in a `.dmg` on GitHub Releases, installed by hand or through a Homebrew cask. This chore builds that path once so every later version is one command.

## What a user gets

```
brew tap martin-gleason/monitormenu https://github.com/martin-gleason/monitormenu
brew trust martin-gleason/monitormenu
brew install --cask monitormenu
```

`MonitorMenu.app` lands in `/Applications`, `monitorctl` is on the PATH, `brew upgrade --cask monitormenu` moves to the next version, `brew uninstall --cask monitormenu` quits the app and removes both, and `brew uninstall --zap` also removes the preferences. The `trust` line is Homebrew 7's rule for every tap outside the Homebrew organisation (verified 2026-10-30: without it Homebrew says "Refusing to load cask … from untrusted tap"). The explicit `tap` line with a URL is because the cask lives in this repository rather than in one named `homebrew-…`; `O17` offers the shorter form.

## Tasks

### C6-T1 — `scripts/release.sh` (packaging)

Owner: agent. Runs `scripts/build-app.sh`, checks that the bundle's version equals `MonitorCore.version`, puts the app and an `Applications` link in a compressed `.dmg` named `MonitorMenu-<version>.dmg` under `dist/`, signs the image with the same Developer ID, and prints its SHA-256. `--notarize` submits the zipped app and then the image to Apple with `xcrun notarytool submit --wait` using the keychain profile named by `NOTARY_PROFILE` (default `MonitorMenu`), staples both, and shows Gatekeeper's verdict with `spctl`. `--update-cask` writes the version and SHA-256 into `Casks/monitormenu.rb`. Without `--notarize` the script says, in its last lines, that the image is not notarized and other Macs will refuse it.

Checkpoint: `scripts/release.sh --update-cask` produces `dist/MonitorMenu-1.0.1.dmg`, mounts, contains a bundle whose `codesign --verify --deep --strict` passes, and the cask's `sha256` equals `shasum -a 256` of the image.

### C6-T2 — `Casks/monitormenu.rb`

Owner: agent. Versioned GitHub Releases URL, SHA-256, `app` and `binary` stanzas (the CLI on the PATH), `uninstall quit:` the bundle id so an upgrade quits the running app, `zap trash:` the preferences plist, `depends_on macos: ">= :sonoma"` and `arch: :arm64` (Package.swift's floor and the DDC path), and a `livecheck` on GitHub releases.

Checkpoint: `brew audit --cask --strict` and `brew style` pass on the tapped cask; `brew install --cask` from a copy of the cask whose `url` is the local `file://` image installs `/Applications/MonitorMenu.app` and `/opt/homebrew/bin/monitorctl`, `monitorctl list` from that path prints the monitor, and `brew uninstall --cask` removes both. (The local test must first move aside the `monitorctl` link that `build-app.sh --install` made, then put it back.)

### C6-T3 — README and repository page

Owner: agent. The Install section leads with the three Homebrew lines, then the `.dmg` from Releases, then building from source. The repository description gains "brew install --cask monitormenu".

### C6-T4 — First published release (procedure; waits on `O16`)

Owner: agent, after the owner runs `xcrun notarytool store-credentials MonitorMenu` once (app-specific password or App Store Connect API key). Then, from `main` after this chore merges:

1. `scripts/release.sh --notarize --update-cask` — notarized, stapled image; cask carries its SHA-256.
2. Commit the cask (`chore(C6): cask points at 1.0.1`), PR, merge.
3. `git tag -a v1.0.1 <merged sha>`, push the tag, `gh release create v1.0.1 dist/MonitorMenu-1.0.1.dmg --notes-file …`.
4. On a Mac that never had the app, or after `brew untap`, run the three install lines; `spctl -a -vv /Applications/MonitorMenu.app` must say `accepted`, `source=Notarized Developer ID`.

Every later version repeats 1–4 with the new number; the cask's `livecheck` lets `brew livecheck --cask monitormenu` confirm the release is visible.

Checkpoint for this chore without `O16`: steps 1–2 run without `--notarize` on this Mac, and the README, cask and script are merged. The release is not published unnotarized: a user who follows the README on another Mac would meet Gatekeeper's refusal, which is worse than no release.

## Risks

- **RR1 unchanged**: Homebrew makes the app easier to get, not more robust to a macOS change.
- **Cask SHA drift**: the notarized image differs from the unnotarized one; the cask in this PR carries the unnotarized SHA-256 and `--update-cask` rewrites it at T4 step 1. The checkpoint in T4 step 4 catches a forgotten rewrite.
- **Two copies on this Mac**: `~/Applications/MonitorMenu.app` (from `build-app.sh --install`) and `/Applications/MonitorMenu.app` (from the cask) would both register the URL scheme. The owner's Mac keeps one; the T2 test uninstalls its copy before finishing.
- **`homebrew/cask` core** is not attempted: it requires notability (stars, forks, age) a new repository does not have. The tap is the right home now; `O17` records the one-line variant.
