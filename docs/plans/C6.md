# C6 — Homebrew distribution: notarized DMG, cask, release procedure

Created: 2026-10-30 09:50 -05:00 · Edited: 2026-10-30 10:10 -05:00

**Status:** gate crossed 2026-10-30 ("let's build this for homebrew. and update the github page to reflect you can get it with homebrew", read as ratifying `D23`); built 2026-10-30; adversarially reviewed the same day, two majors and eleven minors, all but two fixed (`docs/reviews/C6.md`); the first published release (T4) waits on `O16` · **Milestone:** v1.5 · **Owner:** agent

Learning level 5%, locked (`O2`); every task is `owner: agent` except the one keychain step only the owner can perform.

## Why

The Mac App Store cannot take the app (`docs/learnings/2026-10-30-app-store-feasibility.md`, `D23`). Every DDC app on the Mac ships the same other way: a Developer ID signed, notarized, stapled bundle in a `.dmg` on GitHub Releases, installed by hand or through a Homebrew cask. This chore builds that path once so every later version is one command.

## What a user gets

```
brew tap martin-gleason/monitormenu https://github.com/martin-gleason/monitormenu
brew trust martin-gleason/monitormenu
brew install --cask monitormenu
```

`MonitorMenu.app` lands in `/Applications`, `monitorctl` is on the PATH, `brew upgrade --cask monitormenu` moves to the next version, `brew uninstall --cask monitormenu` quits the app and removes both, and `brew uninstall --zap` also removes the preferences. The `trust` line is Homebrew 7's rule for every tap outside the Homebrew organisation (verified 2026-10-30: without it Homebrew says "Refusing to load cask … from untrusted tap"). The explicit `tap` line with a URL is because the cask lives in this repository rather than in one named `homebrew-…`; `O17` offers the shorter form.

## Tasks

### C6-T1 — `scripts/release.sh` (packaging)

Owner: agent. Two modes, exactly one required. `--notarize` (a release): refuses before building if the notarytool keychain profile `NOTARY_PROFILE` (default `MonitorMenu`) is missing or the tree is dirty; runs `scripts/build-app.sh`; checks that the bundle's version equals `MonitorCore.version`; zips the app, submits it with `xcrun notarytool submit --wait`, reads the verdict line (`status: Accepted`, else prints Apple's log and fails), staples the app; puts the app and an `Applications` link in a compressed `.dmg` named `MonitorMenu-<version>.dmg` under `dist/`, signs the image with the Developer ID identity's hash (not its name, which a renewal makes ambiguous), notarizes and staples the image too; prints the SHA-256 and the commit it was built from; shows Gatekeeper's verdict with `spctl`. `--dev` (a local trial): no notarization, dirty tree allowed, and the last line says Gatekeeper refuses the result wherever it carries a quarantine attribute. `--update-cask` writes version, SHA-256 and the Edited stamp into `Casks/monitormenu.rb`; with `--dev` it warns that the checksum is unnotarized and must not be committed. Temporary files are removed on any exit.

Checkpoint: `scripts/release.sh --dev --update-cask` produces `dist/MonitorMenu-1.0.1.dmg`, mounts, contains a bundle whose `codesign --verify --deep --strict` passes, and the cask's `sha256` equals `shasum -a 256` of the image.

### C6-T2 — `Casks/monitormenu.rb`

Owner: agent. Versioned GitHub Releases URL, SHA-256, `app` and `binary` stanzas (the CLI on the PATH), `uninstall quit:` the bundle id so an upgrade quits the running app, `zap trash:` the preferences plist, `depends_on macos: :sonoma` (a bare version in a cask means that version or later; Package.swift's floor) and `arch: :arm64` (the DDC path), and a `livecheck` on GitHub releases.

Checkpoint: `brew audit --cask --strict` and `brew style` pass on the tapped cask; `brew install --cask` from a copy of the cask whose `url` is the local `file://` image installs `/Applications/MonitorMenu.app` and `/opt/homebrew/bin/monitorctl`, `monitorctl list` from that path prints the monitor, and `brew uninstall --cask` removes both. (The local test must first move aside the `monitorctl` link that `build-app.sh --install` made, then put it back.)

### C6-T3 — README and repository page

Owner: agent. The Install section leads with the three Homebrew lines, then the `.dmg` from Releases, then building from source, with a "First release pending" line that T4 removes. The repository description gains the tap-qualified install command at T4, not before: a description that names a command which fails is worse than none (review C6 #1).

### C6-T4 — First published release (procedure; waits on `O16`)

Owner: agent, after the owner runs `xcrun notarytool store-credentials MonitorMenu` once (app-specific password or App Store Connect API key). Then, from `main` after this chore merges:

1. On clean `main`: `scripts/release.sh --notarize --update-cask` — notarized, stapled image; the cask file now carries its SHA-256 (uncommitted).
2. `git tag -a v1.0.1 $(git rev-parse HEAD)`, push the tag, `gh release create v1.0.1 dist/MonitorMenu-1.0.1.dmg --notes-file …`. The asset exists before any checksum that names it is committed, so `brew install` never sees a cask pointing at a missing file.
3. Commit the cask (`chore(C6): cask points at 1.0.1`) together with the README's "First release pending" line removed and the notarization sentence added; PR; merge. The tag sits one commit behind the cask commit, which is fine: the tag marks the source the image was built from, the cask marks where the image is.
4. On a Mac that never had the app, or after `brew untap`, run the three install lines; `spctl -a -vv /Applications/MonitorMenu.app` must say `accepted`, `source=Notarized Developer ID`. Then `gh repo edit --description` gains `brew install --cask martin-gleason/monitormenu/monitormenu`.

Every later version repeats 1–4 with the new number; the cask's `livecheck` lets `brew livecheck --cask monitormenu` confirm the release is visible.

Checkpoint for this chore without `O16`: step 1 runs as `--dev` on this Mac, and the README, cask and script are merged with the README saying the first release is pending. The release is not published unnotarized: a user who follows the README would meet Gatekeeper's refusal, which is worse than no release.

## Risks

- **RR1 unchanged**: Homebrew makes the app easier to get, not more robust to a macOS change.
- **Cask SHA drift**: the notarized image differs from the unnotarized one, and a compressed HFS+ image is not byte-reproducible anyway, so the SHA-256 in this PR matches no asset that will ever be published; `--update-cask` rewrites it at T4 step 1, the script refuses to write an unnotarized checksum without `--dev`, and the checkpoint in T4 step 4 catches a forgotten rewrite.
- **Two copies on this Mac**: `~/Applications/MonitorMenu.app` (from `build-app.sh --install`) and `/Applications/MonitorMenu.app` (from the cask) would both register the URL scheme. The owner's Mac keeps one; the T2 test uninstalls its copy before finishing.
- **`homebrew/cask` core** is not attempted: it requires notability (stars, forks, age) a new repository does not have. The tap is the right home now; `O17` records the one-line variant.
